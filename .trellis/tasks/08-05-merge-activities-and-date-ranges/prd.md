# 活动快捷合并与抖音日期区间解析

## Goal

让后台编辑可以把自动同步后实际属于同一场活动的多个活动快速合并，并让抖音简介中的跨日写法（例如 `8.8～9 深圳金铲铲`）生成正确的完整日期区间。合并结果应在后续抖音同步中保持稳定，同时不能破坏已经发生的活动记录。

## Background and confirmed behavior

- 这是网站 5.0 的增量功能，站点继续部署在 Vercel，不能依赖抖音 OAuth。
- 自动同步只把深圳行程写入“未来活动”；详情页仍展示原始行程文本和小号，首页和活动卡片不新增行程展示。
- 自动分组的现有约束继续有效：同日期同城市可视为同一活动，前后日期间隔不超过 3 天且总跨度最多 5 天；有明确且不同的活动名时不自动合并；活动名缺失时留白。
- 抖音简介更新后，已经从“未来活动”变成“完成”的活动不能因简介删除行程而被自动删除。
- 现有日期解析正则 `src/modules/douyin/itinerary.ts:52` 的日期范围分隔符包含半角 `~`、长横线和“至”，但不包含全角 `～`。这会把 `8.8～9...` 截断为 `8.8`，并把 `～9...` 错当作活动名；解析结果已有 `endDateKey` 字段，可在现有结构上修复。
- 现有深圳活动分组入口为 `src/modules/douyin/itinerary.ts:321`，按标准化活动名分组；因此不同明确活动名会保持独立，图 1 中需要人工处理的拆分属于预期的自动分组边界。
- 后台活动管理器 `src/components/admin/archive-manager-v3.tsx:306` 已有活动勾选、多选和批量删除；批量操作 UI 在 `:1025` 附近，目前只有删除。
- 活动批量 API `src/app/api/admin/events/bulk/route.ts:1`、输入类型 `src/modules/admin/types.ts:25`、校验和 mutation `src/modules/admin/mutations.ts:152,646` 目前只支持删除。
- 活动、阵容和档案分别由 `ContentRepository` 的 `upsertEvent`、`replaceEventLineup`、`saveArchive`、`deleteEvent` 等能力持久化；mock 与 Postgres repository 必须保持一致。
- 当前手工保存活动会将活动标记为 `origin: "manual"`，并通过 `douyin:*` 阵容来源保留或抑制自动同步身份（`src/modules/admin/mutations.ts:437-500`）。

## Requirements

### R1. 修复跨日日期解析

1. 支持与现有写法等价的全角波浪号 `～`，包括省略结束日期月份的写法 `8.8～9`。
2. 跨日结果的开始日期为 `8.8`，结束日期为同年 `8.9`；生成活动时应使用完整区间，不能把 `～9` 留入活动名。
3. 保留现有日期校验、年份推断、原始行程展示和过去活动保留规则。
4. 为全角分隔符、跨日活动名和无效区间补充单元测试，并确保现有半角/中文分隔符测试不回归。

### R2. 后台快捷合并活动

1. 在后台活动管理器中，选择至少两个活动后提供清晰的“合并活动”快捷操作；未选择足够活动时不可执行，并保留现有批量删除能力。
2. 合并操作必须让编辑明确指定一个“保留活动”，并在执行前展示将被合并的活动范围和不可逆删除提示。
3. 合并后的活动应合并所选活动的基础信息、日期区间、达人阵容和现场档案：保留活动名称、场馆和备注，日期取所有来源活动的最早开始日至最晚结束日；阵容按“达人 + 阵容日期”去重；现场档案迁移到保留活动并去重。
4. 合并成功后删除被合并活动及其重复关系，但不能删除或重置保留活动的已有档案、达人记录或资产。
5. 合并操作应是一次有一致性保证的服务端操作；成功或失败都要给出可理解的后台反馈，部分成功不得留下半合并状态。
6. 合并产生的结果必须在下一次抖音同步后保持为一个活动，不得因为原简介中存在多个活动名而又拆回多个活动；同时要保留自动更新，后续简介变化仍能更新该活动关联的抖音行程、日期和达人阵容。
7. mock repository、Postgres repository、API schema、mutation、后台状态刷新及相关测试需要保持契约一致。

## Out of scope

- 不新增抖音 OAuth、开播提醒或其他抖音数据抓取能力。
- 不改变自动同步“只写深圳”的范围，也不把所有简介行程写入活动。
- 本次需要增加最小可追踪的“活动合并覆盖规则”持久化模型，以支持合并后继续自动更新；不扩展为通用的人工规则编辑器或候选审核系统。
- 不自动合并有明确不同活动名的行程；人工快捷合并是本次解决图 1 场景的方式。

## Acceptance Criteria

- [ ] `8.8～9 深圳金铲铲` 在当前年份解析为开始 `YYYY-08-08`、结束 `YYYY-08-09`，活动名称不含 `～9`；半角 `~`、长横线、“至”及无效日期行为保持正确。
- [ ] 后台勾选两个或以上活动时可以选择保留活动并执行合并；少于两个时按钮禁用或明确提示。
- [ ] 合并后保留活动的日期覆盖所有来源活动的最早开始日至最晚结束日，阵容和档案在详情页可见且不重复；被合并活动不再出现在列表中。
- [ ] 合并失败时不会只删除部分活动或只迁移部分关系，后台能看到失败原因。
- [ ] 合并涉及的自动抖音阵容不会在下一次同步中重新创建被拆开的活动；后续简介日期、原文或活动名变化仍能更新同一个保留活动及其来源阵容；过去活动仍不会因简介变化而被删除。
- [ ] 相关单元、mutation/repository、API 和前端交互测试通过，类型检查和项目既有质量检查通过。

## Resolved product decision

用户确认保留自动更新。实现采用“保留活动 + 持久化合并覆盖规则”：编辑指定保留活动；保留其名称、场馆和备注，日期由参与合并的当前来源及后续活跃来源自动取最早开始日至最晚结束日；合并达人阵容和现场档案并去重；被合并活动删除。覆盖规则记录被合并来源的可识别信息，并在每次同步时把匹配到的多个抖音分组汇入同一保留活动，保留 `douyin:*` 来源标记，使日期、原文和阵容仍能自动更新。规则不抑制来源，也不允许同步覆盖保留活动的场馆、备注或编辑选定名称；当来源连续消失时只移除对应来源阵容，保留活动本身不因规则而被自动删除。
